The Estimation Gap: Systematic Cost Underestimation in LLM-Assisted Research, Active Cost Architecture, and a Circuit Breaker Protocol for Spend Control

How AI-assisted citizen science generates unpredictable compute costs — predicting blowup points before they occur, trimming non-linearities during experiments, and a reactive backstop for when those measures are insufficient

Aaron Kushner May 2026 Pre-print · Working paper

Abstract

Researchers using large language model (LLM) APIs to run automated experiments face a class of cost estimation failure not present in classical compute workflows: the billable unit (tokens in context) grows non-linearly with experiment scale in ways that small test runs do not reveal. We document five compounding failure modes — baseline calibration error, context window growth, dataset scaling, pipeline superlinearity, and silent scope expansion — observed in a real multi-agent behavioral study that incurred $8,032 against pre-run estimates of $15–30 (a 78–157× error). Rather than treating this as a monitoring problem solvable by better alerting, we argue for a three-layer approach: (1) pre-experiment cost anatomy analysis that predicts which components of a specific experimental design will enter the non-linear cost regime and at what scale; (2) active cost architecture — code patterns applied during experiments that continuously reduce context volume, route tasks to cheaper models, and decompose superlinear pipelines into linear ones; and (3) a circuit breaker protocol as a reactive backstop for residual risk. Together these layers transform cost from a surprise discovered post-billing into a designed parameter of the experiment itself.

§1. Introduction

The democratization of AI research through API-accessible LLMs has created a new class of citizen scientist: individuals running multi-agent behavioral studies, automated annotation pipelines, and synthetic data generation experiments on commercial model APIs. Unlike classical compute costs — predictable from job size and cluster pricing — LLM API costs are governed by token volume, and token volume is determined by context window contents that grow dynamically as experiments run.

This paper addresses a problem that is poorly understood in practice: standard cost estimation for LLM batch experiments is not merely imprecise — it is systematically wrong by one to two orders of magnitude, because the intuition that produces the estimate (derived from small test runs) does not capture the non-linear growth behaviors that dominate at scale.

Prior work on LLM cost management has focused primarily on monitoring and alerting (Anthropic, 2026; OpenAI, 2024): dashboards that show current spend, rate limits that cap monthly totals, and billing alerts that fire after the damage is done. This paper argues that monitoring is insufficient as a primary control. A spend alert that fires after a $2,355 day has no retroactive value. What is needed is a methodology for predicting where a specific experimental design will blow up, code patterns that prevent that growth from occurring during the run, and a circuit breaker as the final backstop for residual risk.

Central argument: LLM experiment cost is predictable from the mathematical structure of the experimental design, not just from small-sample measurement. Every multi-agent experiment contains identifiable non-linear components whose cost growth can be modeled in advance, mitigated structurally, and bounded by active management during the run. The circuit breaker is the third line of defense, not the first.

§2. Background

2.1 Token-based billing and the context window problem

Commercial LLM APIs bill per token — a subword unit roughly corresponding to 0.75 English words. At the time of writing, claude-sonnet-4-6 is priced at $3 per million input tokens and $15 per million output tokens. A single 500-token exchange costs approximately $0.003. This sub-cent per-call cost creates a perception of cheapness that is accurate for interactive use and systematically misleading for batch experimentation.

The critical variable is context: every API call requires sending the entire conversation history (system prompt + all prior turns) as input. A call at turn 8 of a session costs roughly 5–8× more than a call at turn 1, because the context window carries 7 prior turns of accumulated dialogue. This is not incidental — it is how transformer-based models maintain coherence. But it violates the independence assumption embedded in naive cost estimates, which treat each call as a fixed cost.

2.2 The citizen scientist compute problem

Classical academic compute involves a budget allocation review: you submit a job, a scheduler estimates wall time and cost, and you approve before execution. No equivalent gate exists for LLM API experiments. A Python script can issue an unlimited number of API calls with no pre-flight cost estimate and no automatic stop. The researcher's only native protection is a monthly billing cap — a monthly cap, not a per-run gate, which means a single overnight batch can exhaust it entirely.

For a solo researcher without institutional oversight, a multi-thousand-dollar billing event is not an operational cost — it is potentially the end of the research program. The citizen scientist model requires that solo operators have the same guardrails available to institutional researchers, implemented in tooling rather than requiring organizational infrastructure.

2.3 Existing cost management tools and their limitations

Three categories of tooling address LLM cost management today. Understanding their limitations is necessary context for the approach this paper proposes.

Provider-native monitoring. Anthropic, OpenAI, and other major API providers offer usage dashboards, monthly budget caps, and email alerts when spend crosses a threshold. These are designed for organizational billing management, not per-experiment cost control. A monthly cap fires after the damage is done — it has no mechanism to prevent a single overnight batch from exhausting it. As of this writing, no major provider offers a pre-flight cost estimate, a per-run gate, or an experiment-scoped stop condition in their native tooling.

Third-party spend dashboards. Tools such as api-dash (open source, referenced in §7), Helicone, and LangSmith provide real-time token and cost monitoring at the call level. These improve visibility significantly — a researcher can see spend accumulate in real time rather than discovering it the following day on a billing statement. Visibility is necessary but not sufficient. The May 1 spike in §4 triggered api-dash's daily-ratio alert correctly, within seconds of the threshold crossing. The batch had already completed. A monitor that cannot halt a running process is a post-mortem tool, not a control.

Application-level circuit breakers. The most direct mechanism is a circuit breaker: a component that halts API calls when a spend threshold is crossed. This addresses run-time overruns but not the root cause — a non-linear experimental design that will blow through any reasonable threshold if not restructured. No general-purpose circuit breaker library exists for LLM experiment runners; existing implementations are ad hoc and project-specific.

The shared gap across all three categories:

All intervene after cost is being incurred. None address cost at the experimental design level — before any API calls are made. The methodology described in §§5–8 moves cost management upstream, into the structure of the experiment itself. The circuit breaker (§7) is the third line of defense, not the first.

§3. Taxonomy of Failure Modes

We identify five distinct mechanisms that compound to produce the observed estimation gap.

Failure Mode 1

Baseline Calibration Error

Mechanism: The researcher derives a per-call cost from early test runs using small contexts. As the experiment scales, contexts grow and per-call cost rises, but the baseline estimate remains anchored to the cheap early calls.

Example: A 4-turn test of a single pilot persona costs $0.18. The researcher extrapolates: 8-turn sessions ≈ $0.36, 90-session batch ≈ "$15–30." Actual: $29/session, $2,355 batch.

Error multiplier: 78–157× on batch estimate.

Failure Mode 2

Context Window Growth

Mechanism: Each turn adds to the context window. Cost at turn N is proportional to the sum of all prior turns, making session cost grow approximately quadratically with session length. In a multi-agent setup, the evaluator receives the full session transcript — meaning evaluator cost alone scales quadratically with turns.

Mathematical form: If each turn produces T tokens, total input tokens for a K-turn session ≈ T·K + T·(K-1) + … + T·1 = T·K(K+1)/2 = O(K²).

Error multiplier: 3–4× beyond linear per session; compounds with FM1.

Failure Mode 3

Dataset Scaling

Mechanism: As studies scale from pilot to full, researchers enrich their data: larger persona profiles, more detailed system prompts, longer experimental protocols. Each enrichment is a constant multiplier on every API call in the experiment. A 10× richer persona file means every persona call, companion call, and evaluator call costs 10× more than pilot calibration suggested.

Example: personas_pilot.json (5 compact profiles, ~15KB) was used for cost calibration. personas_full.json (31 detailed profiles, 246KB) was used for the actual run. Average system prompt grew ~10× between pilot and production.

Error multiplier: 5–10× per call vs. pilot calibration.

Failure Mode 4

Pipeline Superlinearity

Mechanism: Experiment runners commonly include post-processing pipelines (paper generation, claim verification, cross-model analysis) that pass the full batch output as a single context. The cost of these calls is proportional to total transcript volume, which grows with N²: N sessions each producing transcripts that grow with session depth. These calls are typically added as convenience features after initial cost estimates are made, and are never included in estimates.

Mathematical form: N sessions × K turns × T tokens/turn = N·K·T total transcript tokens. The synthesis call receives all of this as input: O(N·K·T). If N and K both grow, this is O(N²) in the worst case.

Error multiplier: Unbounded — never modeled in estimates.

Failure Mode 5

Silent Scope Expansion

Mechanism: Batch runners execute all "missing" experiment combinations automatically. Adding new conditions or personas to a config file silently expands the queue beyond what the researcher consciously authorized. The "already done" check calculates remaining work from a new, larger total.

Example: An expected small incremental batch ("~$5.40") grew to 51 uncompleted combinations after new conditions were added to the config, producing $955 — a 177× error before the first session ran.

Error multiplier: Proportional to unnoticed queue growth.

§5. Predicting Blowup Points Before Running

Every experimental design has an identifiable cost structure that can be analyzed before any API calls are made. The goal of cost anatomy analysis is to decompose the experiment into components, classify each as linear or non-linear in the scaling dimensions, and identify the scale at which each component will exit the "cheap" regime.

5.2 The non-linear regime threshold

Once components are classified, the threshold at which each enters the expensive regime can be estimated analytically. For context window growth (FM2), the inflection point depends on turn depth and token density. For a typical companion interaction where each turn produces ~500 tokens:

  • Turn 1: ~2KB context → ~$0.006
  • Turn 4: ~8KB context → ~$0.024
  • Turn 8: ~24KB context → ~$0.072 (3× what linear scaling predicts)
  • Turn 12: ~50KB context → ~$0.150 (6.25× linear prediction)

The quadratic growth doesn't feel painful at small K. At K=8 it's a 3× surprise; at K=12 it's a 6× surprise. Before setting turn depth, a researcher should plot this curve for their specific token density and ask: at what turn depth does this become unacceptable?

For dataset scaling (FM3), the threshold is simpler: the ratio of production persona file size to pilot persona file size is a direct cost multiplier. If your production profiles are 10× larger than your pilot profiles, every call costs 10× more. This should be measured explicitly: 

# Measure before running
import json
pilot = json.load(open("personas_pilot.json"))
full  = json.load(open("personas_full.json"))

avg_pilot_chars = sum(len(json.dumps(p)) for p in pilot) / len(pilot)
avg_full_chars  = sum(len(json.dumps(p)) for p in full)  / len(full)

print(f"Pilot avg profile: {avg_pilot_chars:.0f} chars")
print(f"Full  avg profile: {avg_full_chars:.0f} chars")
print(f"Scaling multiplier: {avg_full_chars / avg_pilot_chars:.1f}×")
# → Scaling multiplier: 9.3×  ← this is what should have been caught

For pipeline superlinearity (FM4), the blowup point is when N × transcript_size exceeds the model's comfortable context. At 90 sessions of 8 turns each, total transcript volume is approximately 90 × 8 × 1000 tokens = 720,000 tokens. A single synthesis call ingesting this costs roughly $2.16 in input alone — before any output. That number should appear in the pre-run estimate.

5.3 The pre-run cost projection

A correct pre-run projection combines all components with their actual growth functions, using one real token-sampled session as the calibration point: 

# After running one real session:
session_tokens_in  = <from API response usage.input_tokens>
session_tokens_out = <from API response usage.output_tokens>
price_in  = 3.00 / 1_000_000   # $/token for claude-sonnet-4-6
price_out = 15.00 / 1_000_000

cost_per_session = session_tokens_in * price_in + session_tokens_out * price_out

# Session costs grow due to FM2 — apply growth factor
# (approx: sessions later in batch have larger context from personas_full.json)
growth_factor = 1.5  # conservative; measure from runs 1, 5, 10 of a test batch

# Dataset scaling factor
profile_multiplier = avg_full_chars / avg_pilot_chars  # from measurement above

# Synthesis pipeline overhead
N_sessions = len(queue)
K_turns = n_turns
synthesis_tokens_in = N_sessions * K_turns * 800  # conservative estimate
synthesis_cost = synthesis_tokens_in * price_in

total_estimate = (
    N_sessions * cost_per_session * growth_factor * profile_multiplier
    + synthesis_cost
)

print(f"Sessions: {N_sessions}")
print(f"Base cost/session: ${cost_per_session:.2f}")
print(f"With growth + scaling: ${cost_per_session * growth_factor * profile_multiplier:.2f}/session")
print(f"Synthesis pipeline: ${synthesis_cost:.2f}")
print(f"TOTAL PROJECTED: ${total_estimate:.2f}")
print()
input("Press Enter to proceed, Ctrl+C to abort: ")

If this projection had existed on April 22, it would have shown approximately $800–1,200 for the 90-session batch, not $15–30. That number might still have been approved — but it would have been a deliberate decision.

§6. Active Cost Architecture: Trimming the Fat During Experiments

Accurate projection tells you how much an experiment will cost. Active cost architecture tells you how to redesign the experiment so that it costs less without sacrificing the research question. The goal is not to run cheaper experiments — it is to spend money on the parts of the experiment that require expensive compute, and use cheap compute everywhere else.

6.1 Model routing by task complexity

The single highest-leverage intervention available to any LLM experiment designer is model routing: using the cheapest model capable of each specific subtask, rather than the most capable model for all subtasks. In the ai-companion study, three agent types each used claude-sonnet-4-6 ($3/$15 per MTok). Only one of them needed it.

Active Mitigation 1

Model Routing Table

For each component in your experiment, ask: what is the minimum capability required? Structured generation from a template (persona messages) and structured scoring (1–5 evaluator rubric) do not require frontier reasoning. Only tasks requiring genuine synthesis, nuance detection, or open-ended writing do.

TaskFrontier needed?Recommended modelCost vs. Sonnet
Persona message generation No — follows template Haiku 4.5 ~20× cheaper
Companion response (core product) Yes — this is the thing being tested Sonnet 4.6 Baseline
Per-turn evaluator scoring No — structured rubric, 1–5 scores Haiku 4.5 ~20× cheaper
Session-level qualitative scoring Borderline — use Sonnet if nuance matters Haiku 4.5 or Sonnet ~5–20× cheaper
Memory consolidation No — summarization task Haiku 4.5 ~20× cheaper
Synthesis / paper writing Yes — reasoning over full results Sonnet 4.6 or Opus Baseline
Claim verification (cross-model) No — fact-check against data Gemini Flash / GPT-4o mini ~10× cheaper

In the ai-companion study, approximately 70% of API calls were persona generation and per-turn evaluation — neither of which required Sonnet. Routing those to Haiku would have reduced the $8,032 total to approximately $1,200–1,800, with no change to the experimental results (the companion responses and final scoring, the actual dependent variable, remain on Sonnet).

6.2 Context window management: rolling summarization

FM2 (context window growth) is the most structurally damaging failure mode because it is inherent to the conversational format. It cannot be eliminated — but it can be bounded. The key insight is that a session at turn 8 does not need turns 1–3 verbatim. It needs the meaning of turns 1–3, which is much smaller.

Active Mitigation 2

Rolling Window with Summarization

Maintain a fixed-size verbatim window (e.g., last 3 turns) and a rolling summary of all earlier turns. Before each call, prepend the summary as a brief context block. This converts O(K²) context growth to O(K) with a small constant overhead for the summary.

def build_context(transcript: list[dict], verbatim_window: int = 3) -> list[dict]:
    """
    Returns a context list for the next API call.
    Older turns are compressed into a summary block; only the last
    `verbatim_window` turns are sent verbatim.

    Cost profile: O(verbatim_window) instead of O(K²).
    """
    if len(transcript) <= verbatim_window:
        return transcript  # early session — no compression needed

    older   = transcript[:-verbatim_window]
    recent  = transcript[-verbatim_window:]

    # Summarize older turns (using Haiku — this is cheap)
    summary_text = summarize_turns(older)  # single Haiku call

    summary_msg = {
        "role": "user",
        "content": f"[Session context so far — turns 1–{len(older)}]\n{summary_text}"
    }
    # Return: [summary block] + [last N turns verbatim]
    return [summary_msg] + recent

A rolling window of 3 verbatim turns with a compact summary caps per-call context at approximately 4–6KB regardless of session depth, compared to 24–50KB for an unbounded 8–12 turn session. The summarization calls add a small cost (one cheap Haiku call per summarization event) but eliminate the quadratic growth entirely.

Critically, the research question is not harmed by this approach. In a behavioral study, what matters is whether the companion maintains its values under pressure over time — a pattern that is preserved in a good summary. The exact wording of turn 2 is not usually what the research question is measuring.

6.3 Persona profile compression

FM3 (dataset scaling) arises when rich persona profiles are sent wholesale on every call, including fields irrelevant to the current turn. A persona file designed for flexibility contains biographical detail, psychological history, behavioral tendencies, relationship patterns, and experimental condition overrides — most of which are not needed on every call.

Active Mitigation 3

Condition-Scoped Persona Projection

Before each experiment run, project the full persona profile down to the fields required by the specific condition and session number. Pass the projection, not the full profile. The full profile remains available for reference but is not transmitted on every API call.

def project_persona(persona: dict, condition: str, session: int) -> dict:
    """
    Extract only the fields needed for this condition × session.
    Reduces system prompt by 60–80% for structured conditions.
    """
    base = {
        "name":        persona["name"],
        "background":  persona["background"],       # always needed
        "presenting":  persona["presenting_issue"],  # always needed
    }
    if condition in ("LA", "LB", "LC"):  # longitudinal — needs history
        base["session_history"] = persona.get("session_history", [])[:session]
    if condition == "adversarial":
        base["vulnerabilities"] = persona.get("vulnerabilities", [])
    # Drop: full_biography, relationship_map, future_goals, etc.
    return base

In the ai-companion study, persona profiles in personas_full.json averaged ~8KB each. A condition-scoped projection reduces this to ~1–2KB, a 4–8× reduction in system prompt size and a corresponding reduction in per-call cost across the entire experiment.

6.4 Synthesis pipeline decomposition

FM4 (pipeline superlinearity) is caused by feeding an entire batch of transcripts into a single synthesis call. At 90 sessions, this creates a context of hundreds of thousands of tokens — and the cost is paid once, at the end, in a single call that cannot be interrupted by the circuit breaker until it completes.

Active Mitigation 4

Map-Reduce Synthesis

Replace one large synthesis call with a two-pass pipeline: first, summarize each session independently (small O(K) calls); then synthesize the summaries (small constant-size input regardless of N). This converts O(N·K) synthesis cost into N·O(K) + O(N) — linear in both N and K separately.

BEFORE: all 90 transcripts → one Sonnet call → paper [O(N·K) tokens in]

AFTER:
session 1 transcript → Haiku summary → 200-token abstract
session 2 transcript → Haiku summary → 200-token abstract
... (N Haiku calls, each O(K)) ...
90 abstracts (18,000 tokens) → Sonnet synthesis → paper [O(N) tokens in]

Cost: N × O(K) cheap + one O(N) expensive vs. one O(N·K) expensive
At N=90, K=8: ~$0.08 per summary + ~$0.05 synthesis vs. ~$2.16 monolithic

The map-reduce approach also makes the synthesis interruptible: if the circuit breaker triggers after 45 session summaries, the batch can resume from summary 46 rather than starting over. Each summary is a cheap, stateless call.

6.5 Turn-depth budgeting

Turn depth is a free parameter in most multi-turn studies, but its cost implications are rarely treated as a design variable. Because session cost grows quadratically with K (FM2), the optimal turn depth is not the maximum depth that fits the research question — it is the minimum depth at which the research question can be reliably answered.

Active Mitigation 5

Early Stopping on Rubric Saturation

If the research question is answered when certain rubric scores stabilize, add a stopping criterion: end the session when the evaluator's last N scores show no variance above a threshold. This preserves research validity (you ran until the signal was clear) while eliminating the "last few turns" that often carry the highest context cost for the lowest informational value.

def scores_saturated(score_history: list[dict], window: int = 3, tol: float = 0.5) -> bool:
    """True if the last `window` scores show negligible variance."""
    if len(score_history) < window:
        return False
    recent = score_history[-window:]
    for key in ["felt_heard", "values_maintained", "dependency_free"]:
        vals = [s.get(key, 0) for s in recent]
        if max(vals) - min(vals) > tol:
            return False  # still moving — keep going
    return True  # converged — safe to stop early

In practice, rubric saturation often occurs at turn 5–6 in well-designed studies, meaning turns 7–8 add cost but not signal. At 90 sessions, eliminating two turns per session would have saved approximately 22% of total cost — a meaningful amount at these scales.

§7. The Circuit Breaker Protocol

With proactive cost anatomy (§5) and active cost architecture (§6) applied, a well-designed experiment should not blow up. But residual risk remains: estimates are imperfect, experimental designs evolve mid-study, and silent scope expansion (FM5) can still produce unexpectedly large queues. The circuit breaker is the reactive backstop for these residual cases.

7.1 Design principles

The circuit breaker pattern (Nygard, 2007) requires: a shared signal channel between monitor and runner; a check at every billable operation; fail-open semantics when the monitor is down; and human-in-the-loop resumption. The file system is the simplest shared channel: the monitor writes a JSON file; the runner reads it before each session.

7.2 Implementation

The spend monitor (api-dash) writes ~/.api-dash/throttle.json whenever its spike detection logic triggers or any throttle state changes:

{
  "anthropic": {
    "triggered": true,
    "paused": false,
    "reason": "today $955.09 is 2.8x daily avg ($344.46)",
    "triggeredAt": "2026-05-02T00:56:21.205Z"
  }
}

The experiment runner checks this file via a single-module import before each session:

from circuit_breaker import check, CircuitOpen

# In the batch loop, before each API call:
check("anthropic")   # raises CircuitOpen if triggered; warns if monitor is down

Placing the check in the provider's complete() method catches all API calls through a single chokepoint regardless of which script is running.

If you find yourself relying on the circuit breaker routinely, it means cost anatomy (§5) and active cost architecture (§6) were not applied. The circuit breaker should fire rarely, and when it fires it should be a surprise — evidence of an unanticipated edge case, not a routine cost management tool.

§8. The Complete Spend Control Stack

The three layers operate in sequence, each addressing the failure modes the previous layer does not reach:

Layer 0 — Before you design the experiment

Write the cost anatomy (§5.1). Identify every O(K²) and O(N·K) component. Plan the active mitigations (§6) before writing any experiment code. This is not overhead — it is how you convert a potentially runaway experiment into a bounded one.

Layer 1 — Before you run (pre-flight)

  1. Measure the dataset scaling multiplier (§5.2) by comparing production vs. pilot profile sizes
  2. Run one token-sampled session (§5.3) and compute the projected total cost using the growth formula
  3. Display the projection and require explicit confirmation before launching the batch
  4. Run --dry-run to enumerate the complete queue and confirm session count (FM5 mitigation)

Layer 2 — During the run (active management)

  1. Route tasks to appropriate models (§6.1) — most calls go to Haiku
  2. Apply rolling summarization (§6.2) — context window stays bounded
  3. Use condition-scoped persona projections (§6.3) — system prompts stay small
  4. Use map-reduce synthesis (§6.4) — no superlinear synthesis calls
  5. Apply early stopping on rubric saturation (§6.5) — no wasted turns

Layer 3 — Reactive backstop

Circuit breaker (§7) running throughout. Fires if layers 0–2 miss something.

At 274 sessions, applying model routing (70% Haiku), rolling summarization (3-turn window), persona compression, and map-reduce synthesis, projected cost drops from $8,032 to approximately $400–800. The research question — does the values-calibrated companion maintain its protocol under pressure — is answered identically. Only the compute cost changes.

§9. Proof of Protocol

Validating the complete stack requires demonstrating two things: (1) the active mitigations reduce cost without degrading research validity; (2) the circuit breaker halts correctly when it fires.

Proof procedure — active mitigations

  1. Run the same 5 pilot personas under the original architecture (all Sonnet, full context, full profiles). Record cost and scores.
  2. Run the same 5 pilot personas under the mitigated architecture (routed models, rolling window, compressed profiles). Record cost and scores.
  3. Compare scores: the dependent variables should be statistically indistinguishable. Compare cost: the mitigated run should be 70–85% cheaper.

Proof procedure — circuit breaker

  1. Start a batch with the circuit breaker active. Confirm the signal file is present.
  2. Use the dashboard's test endpoint (POST /api/throttle/test) to synthetically trigger the throttle mid-run.
  3. Confirm the batch receives CircuitOpen and exits cleanly within one session boundary.
  4. Dismiss the throttle. Confirm the signal file updates. Confirm the next run proceeds normally.

§10. Discussion

10.1 Estimation vs. architecture

The standard response to cost estimation failure is to try harder to estimate: gather more data points, refine the model, add uncertainty bounds. This paper argues that better estimation is insufficient as the primary control, for a structural reason: the non-linearities that cause estimation failure (FM2, FM4) are not estimation errors — they are properties of the experimental architecture. You cannot estimate your way out of a quadratic growth function. You have to eliminate the quadratic.

This is the distinction between cost prediction and cost architecture. Prediction tells you how much an experiment will cost given its current structure. Architecture changes the structure so the cost is lower. Both are necessary; architecture is primary.

10.2 The meta-irony of AI cost estimation

The estimates that precipitated the $8,032 incident were produced by an AI assistant — the same model (claude-sonnet-4-6) being billed for the experiment. The AI was asked to estimate the cost of running itself at scale. It produced estimates that were accurate for small cases and wrong by two orders of magnitude for the actual scale.

This is not a failure of the model's arithmetic. The model correctly computed cost = sessions × $/session for the session cost it had observed. The failure was structural: the estimator did not have access to the real-time token counts that would have revealed the growth trajectory, and it did not model the pipeline superlinearity because the pipeline feature had been added informally after the initial cost framing.

The fix is not to ask the AI for a better estimate. It is to close the loop between the estimator and the actual token counts — giving it ground truth via token sampling rather than requiring it to reason from first principles about a system whose properties it cannot observe. This is precisely what the token-sampled projection in §5.3 provides.

10.3 Implications for citizen science

For a solo researcher without institutional budget oversight, these failure modes are not inconveniences — they are existential risks to the research program. The $8,032 incident described here incurred in a 10-day window and was not caught until the billing dashboard was reviewed. For a researcher operating on a personal budget, this can represent months of funding capacity for a research program.

The tools described in this paper — cost anatomy analysis, active cost architecture, circuit breaker — are not technically complex. They require no special infrastructure beyond what any Python developer has access to. What they require is a methodological norm: that cost be a designed parameter of every LLM experiment, specified before the first API call, managed actively during the run, and bounded by a reactive backstop. This norm does not yet exist in the citizen science AI community. This paper is a proposal to establish it.

10.4 Limitations

  • Polling latency: The circuit breaker polls billing APIs every 60 seconds. A spike within one polling window (e.g., a single enormous synthesis call) may not be caught in time to halt the current session.
  • Rolling summarization fidelity: In experiments where exact conversational history matters (e.g., studying memory recall), rolling summarization may alter the research condition. The mitigation should be applied only where semantic compression is acceptable.
  • Model routing validity: Routing evaluators to Haiku is appropriate when rubric scoring is the task. For studies where the evaluator's qualitative judgment is itself a research variable, cheaper models may introduce capability confounds.
  • Single-machine scope: The file-system signal channel works only when monitor and runner are on the same machine. Distributed pipelines require an HTTP-based check.

§11. Conclusion

LLM API batch experiments are susceptible to cost overruns not because they are inherently expensive but because their cost structure is non-linear in ways that small-scale tests do not reveal. We documented five failure modes and showed that their compound effect produced a 78–177× estimation error in a real study. We argued that the correct response is not better monitoring but better architecture: cost anatomy analysis that identifies non-linear components before any code is written, active cost management patterns that eliminate those non-linearities during the experiment, and a circuit breaker as a final backstop for residual risk.

Applied together, these layers reduce the projected cost of the documented study from $8,032 to approximately $400–800 with no reduction in research validity. They transform cost from a post-billing surprise into a designed property of the experiment — which is where it belongs.
